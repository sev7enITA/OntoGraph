0:25 · The library and the project code

Take a library. Two copies of a book share one ISBN. A member borrows one, the app marks the title as borrowed, and both copies disappear. Nothing crashed. The app never knew a book from a copy. Or take one project code. Finance reads it as a ledger entry. The project office reads it as a deliverable. Both are right. The application picks one meaning, and never tells you which. And this is not only vibe coding. Carefully engineered systems carry the same gap, because the meaning was never written down. Add AI agents, and the confusion repeats at machine speed.

1:11 · A model agents can read

So we did the groundwork. A dictionary, so every term has one definition. A taxonomy, so every term has a class. An ontology, so every relationship has a type. Three layers, one model: written once, reviewed by people, readable by agents. That makes the model ready for agentic AI. An agent no longer guesses from rows. It asks the graph, follows typed relationships, and returns an answer you can trace to a definition a person approved. This is OnToGraPh. Ontology-driven governance for AI and agents. Govern the rules. Verify the decisions. Four letters, four commitments. O: an operational ontology, where definitions link to processes, controls and applications. T: traceability to every field. G: governance with human authority; people approve, monitor, and can withdraw. P: proof of behavior; evidence of what each application actually did.

2:28 · Aurora 21 and withdrawal

Here is why that last letter matters. In Aurora 21, a synthetic case, one rule feeds two applications. Both report the same release. The CRM applies the new rule. The PMS returns the old decision, behind a matching receipt. A matching receipt is not proof. Withdrawal works the same way. If an application is unreachable, it stays unverified. Never assumed. Only a fresh observation proves the rule has stopped. So where does it sit in the market? Catalogs, ontology editors and graph engines do valuable work: they verify the model and the platform. OnToGraPh verifies behavior after release; what each application actually decided. Keep your platform, and add the layer that proves it.

3:31 · Run it locally

And you can use it today. Clone the repository, run the demo, start the Studio. Four commands. Python and SQLite, nothing else. It runs offline, on your machine, and reproduces Aurora 21 in front of you.

0:00 · Hidden risks

A reader brings two identical books to the desk. You scan the first, lend it out, and the second disappears from the list of available copies. The app did exactly what the code told it to do. Scan the code on screen to try this case yourself.

0:19 · The shared mistake

An AI assistant can make that mistake in a prototype. An experienced engineer can make it in a carefully tested system. If the test data contains only one copy per edition, every test can pass. An ISBN identifies the edition. When I lend a book, I lend one physical copy. That distinction changes who gets to borrow the book.

0:45 · Agent-ready ontology

With OnToGraPh’s agent-ready ontology, an agent can check what a code means before acting. Charge this expense to WBS 0017. In Finance, that code identifies a posting object. In the project office, it identifies a work package. The agent pauses and asks: Which department do you mean, Finance or the project office? The agent waits for your answer. The expense stays on hold.

1:11 · Start here

On the homepage, open Hidden Risks and choose Describe my app. Here is a different brief. A community group assigns volunteers to shelters. A night shift is a type of shift. A shift depends on a volunteer. Generate the proposal. The browser uses local language patterns and keeps the description in this tab until you open it in Studio.

1:38 · Read the proposal

Look at the suggested risk. If the same assignment arrives twice, is it a retry or a second shift? The dictionary proposes terms from the brief. The taxonomy groups them. The ontology connects the assignment, volunteer and shelter. These are suggestions. The person who schedules the shifts can correct a definition before anyone builds on it.

2:04 · Review it

Choose Review in Studio and sign in. The case opens in its own workspace. Expand a dictionary entry, edit the definition, apply the change and save the draft. Reopen the workspace to see the saved revision. You can also download the model as JSON and use the standalone Studio locally with Python and SQLite.

2:29 · Test the consequence

Now consider two departments using the same project code. In our recorded pilot, a spreadsheet acknowledged a new rule and still counted two thousand euros of eligible budget. The corrected workbook counted eight hundred. After withdrawal it still counted eight hundred. A later reading of zero verified withdrawal for those records. The applications were real. The records and review roles were synthetic.

3:34 · Where it fits

Different tools answer different questions. NVIDIA Auto Ontology builds semantic reasoning layers. OntoBricks maps ontologies onto Databricks tables. Genie answers business questions using governed data. Stardog supports graph queries and inference. Drools executes business rules. OntoGraph connects a reviewed meaning to the behavior observed in the receiving application, including what happens after a rule is withdrawn.

4:06 · Optional paths

OnToGraPh began as the shared ontology layer for PALO Framework and PolicyWatcher. Today this open-source framework runs independently. If an external policy changes, PolicyWatcher can supply source evidence. If a decision needs a governance review, PALO can receive the case. In the recorded integration pilot, PolicyWatcher was read only and a local PALO case remained open for a human decision. Opening an optional path sends nothing from your draft.
