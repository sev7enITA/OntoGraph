0:00 · 从隐性风险到可验证的决策

软件交付从未如此之快。这里是 OnToGraPh。接下来的五分钟，我们来看看快速交付容易忽略什么。扫码即可跟随演示。你描述了一个应用。几秒钟后，它就运行起来了。测试全部通过，大家转向下一项工作。但没人问一个代码无法回答的问题：这些词到底是什么意思？

0:25 · 图书馆与项目编码

以图书馆为例。同一本书的两册副本共用一个 ISBN。读者借走一册，应用把整个书目标记为已借出，两册都从可借列表中消失了。程序运行正常，却一直没有区分书目和单册。再看一个项目编码。财务部门将它理解为账目。项目管理办公室则将它理解为交付物。两种理解都有道理。应用自行选择了一种含义，却从不说明选了哪一种。这种问题也会出现在氛围编程之外。即使系统经过精心设计，只要没有写明术语含义，也会留下同样的空白。加入 AI 智能体后，混淆就会以机器的速度反复发生。

1:11 · 智能体可读取的模型

因此，我们先打基础。用词典给每个术语明确定义。用分类体系明确每个术语的类别。用本体明确每种关系的类型。三个层次，一个模型。编写一次，由人审核，智能体可以读取。这样的模型可以供 AI 智能体使用。智能体无需逐行猜测。它可以查询图谱，沿着类型明确的关系查找，给出能够追溯到人工批准定义的答案。这就是 OnToGraPh，以本体驱动 AI 与智能体治理。治理规则，验证决策。四个字母，四项承诺。O，可操作的本体。将定义关联到流程、控制措施和应用。T，每个字段都可追溯。G，人掌握治理权。人可以批准、监控和撤回。P，用行为证据说明每个应用实际做了什么。

2:28 · Aurora 21 与规则撤回

最后一个字母为什么重要？在合成案例 Aurora 21 中，一条规则供两个应用使用。两个应用都报告了同一发布版本。CRM 执行了新规则。PMS 的回执虽然匹配，返回的却是旧决策。仅有匹配的回执不足以证明规则已执行。撤回时也是如此。如果无法访问某个应用，其状态就保持为尚未验证，不能靠推测判定。只有新的观测才能证实规则已停止执行。它在市场中如何定位？数据目录、本体编辑器和图引擎都发挥着重要作用：它们验证模型和平台。OnToGraPh 验证发布后的行为，检查每个应用实际上作出了什么决定。保留现有平台，再加上一层验证。

3:31 · 在本地运行

无需替换现有组件。可以保留目录、图引擎和流水线。OnToGraPh 支持 JSON、JSON-LD、SKOS、OWL 和 PROV-O 等开放格式与标准。它还可以把审核过的规则编译成 Rego。现在就能使用。克隆仓库，运行演示，启动 Studio。四条命令，只需要 Python 和 SQLite。你可以在本机离线运行，亲自复现 Aurora 21。

0:00 · 隐性风险

读者拿着两本相同的书来到借阅台。你扫描并借出第一本，第二本却也从可借清单中消失了。应用准确执行了代码里的指令。扫描屏幕上的二维码，亲自试试这个场景。

0:19 · 共有的错误

AI 助手在原型中可能犯这个错误。经验丰富的工程师在经过严密测试的系统中也可能犯同样的错误。如果测试数据中每个版本都只有一本书，所有测试都可能通过。ISBN 标识的是出版物的版本。借出一本书时，交给读者的是一个具体的实体副本。这个区别决定了下一位读者还能否借到书。

0:45 · 面向智能体的本体

借助 OnToGraPh 面向智能体的本体，智能体可以在行动前核对编码的含义。请将这笔费用记到 WBS 0017。在财务部门，该编码指一个记账对象。在项目管理办公室，该编码指一个工作包。智能体暂停操作并询问：“你指的是哪个部门，财务部门还是项目管理办公室？”智能体等待你的答复。这笔费用暂缓入账。

1:11 · 从这里开始

在首页打开“隐性风险”，选择“描述我的应用”。换一个例子。一个社区组织将志愿者分配到避难所。夜班是班次的一种。每个班次都依赖一名志愿者。生成提案。浏览器使用本地语言规则；在选择用 Studio 打开之前，描述保留在当前标签页中。

1:38 · 阅读提案

看一下系统建议核查的风险。同一项分配收到两次，是重试，还是多排了一个班次？词典从应用描述中提取候选术语。分类体系将这些术语分组。本体描述分配、志愿者和避难所之间的关系。这些都是建议。排班人员可以在其他人使用模型之前修正定义。

2:04 · 复核草稿

选择“在 Studio 中复核”并登录。场景会在独立的工作区中打开。展开一个词条，修改定义，应用更改，然后保存草稿。再次打开工作区即可查看已保存的修订。也可以下载 JSON 模型，在本地使用 Python 和 SQLite 运行独立版 Studio。

2:29 · 验证结果

再看一下两个部门使用相同项目编码的场景。在有记录的试点中，电子表格已确认收到新规则，却仍然计入了两千欧元的预算。使用正确的工作簿后，计入的金额为八百欧元。撤回规则后，表格仍计入八百欧元。后来读到零欧元，才证实这些记录的规则已撤回。试点使用了真实的应用程序。数据记录和复核角色均为模拟。

3:03 · 探索平台

引导路径涵盖个人图书馆、跨部门编码、Copilot 术语表和政策变更。每条路径都有起始模型和检查项。在“加权关系”中，比较证据可信度与错误映射的后果。使用架构拼图探索缺少组件时的影响。在交付流水线中，策略编译器可以把经过复核的规则转换为可在持续集成中测试的产物。

3:34 · 市场定位

不同的工具回答不同的问题。NVIDIA Auto Ontology 构建语义推理层。OntoBricks 把本体映射到 Databricks 表。Genie 基于受治理的数据回答业务问题。Stardog 支持图查询和推理。Drools 执行业务规则。OnToGraPh 将经过复核的含义与接收应用中的实际行为关联起来，包括规则撤回之后发生的情况。

4:06 · 可选路径

OnToGraPh 最初为 PALO Framework 和 PolicyWatcher 提供共享本体层，如今，这个开源框架可以独立运行。如果外部政策变化，PolicyWatcher 可以提供来源证据。如果决策需要治理复核，PALO 可以接收案例。在有记录的集成试点中，PolicyWatcher 只提供读取权限，本地 PALO 案例保持开放，等待人工决定。打开可选路径不会发送草稿内容。

4:33 · 你的第一个场景

选一个两个人理解不同的术语。写一个应通过的例子，再写一个应暂缓的例子。扫描第一个二维码，试用自己的应用场景。第二个二维码通往源代码、示例模型和本地安装说明。把结果交回给决策负责人。这样，能运行的原型就可以成为在这个具体场景中值得信赖的模型。
